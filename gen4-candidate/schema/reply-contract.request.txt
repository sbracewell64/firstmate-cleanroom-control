Rules the consumer enforces mechanically (a violation is refused, never repaired):
  - additionalProperties is false on every object: an unknown or misspelled field
    name is REFUSED_MALFORMED and the refusal names the field.
  - schema: Compared by EXACT STRING EQUALITY, never by substring or prefix. 'fm-sol-control/v2'
      contains 'fm-sol-control', so a consumer matching on word overlap would consume
      retired-venue v1 traffic. See venue_isolation.match_rule in the canonical control config.
  - request_id: EXPLICIT AND STABLE. Derived, never assigned; the inputs and their order are
      owned by $defs.id_derivation in this file and are read from there rather than transcribed.
      Recompiling the same request at the same generations yields the same id, so 'have I
      already asked this?' is a lookup and not a judgement; any generation moving yields a
      DIFFERENT id, so a stale ruling cannot even address the new subject.
  - correlation_id: Derived; inputs and order owned by $defs.id_derivation. Venue unit is one
      issue per correlation_id, which bounds the comment universe so the completeness predicate
      is cheap and always satisfiable.
  - work_id: The durable identity of the WORK this decision belongs to, stable across every
      request generation about it.
  - project: The logical project. Routing and diagnostic metadata only: it is NEVER proof of
      ruler identity or authority. Authority is grounded in the typed ruling, exact request
      parentage, forge venue and identity evidence, and fresh applicability checks.
  - work_generation: Increments when the WORK's own subject or acceptance contract moves. A
      ruling naming an older work_generation is inapplicable.
  - request_generation: Increments per re-ask within one work_generation, e.g. after
      INSUFFICIENT_EVIDENCE. A ruling naming an older request_generation is inapplicable.
  - control_config_generation: Captain addendum, 2026-09-02. ONE canonical owner names the
      protocol, the control repository, the logical Browser Sol project and the routing
      metadata; ONE deterministic resolver normalizes it; digest = sha256 over the canonical
      normalized bytes. Every envelope carries the generation it was compiled against. At
      consumption the consumer FRESHLY RE-RESOLVES the current effective config and compares: a
      mismatch means the ruling stays historical evidence with outcome REFUSED_STALE_CONFIG and
      ZERO action. resolver_digest is the sha256 of the resolver itself, so an emitter and a
      watcher resolving through different resolver bytes is detectable rather than assumed away.
  - venue: The CONTROL venue this request is posted in. Must equal the repository resolved from
      the canonical control config; a request compiled for any other venue is refused before
      emission.
  - repo: The SUBJECT repository identity, exact.
  - acceptance_policy: The acceptance policy in force for this decision, as a named generation
      and a digest over its exact inputs. Compared by identity at consumption; a moved policy
      digest is RULING_SUPERSEDED and needs a new request, which is a different fact and a
      different repair from a moved subject head.
  - valid_while: THE STALENESS LADDER'S INPUTS. All are identity comparisons against LIVE reads
      at consumption. evidence_digest is sha256 over the canonical sorted list of
      'kind\tlocator\tsha256' triples, one per line, LF-terminated: a ruling bound to a request
      id is not thereby bound to the evidence its ruler was shown (v1 CHANGE 4).
  - reply_contract: GENERATED by walking this file. No pre-filled ruling skeleton is ever
      shipped: supplying the phrasing supplies a template, and a template can be filled without
      the underlying fact becoming true (v1 CHANGE 1). The renderer self-checks by re-rendering
      after posting and byte-comparing.
  - routing_labels: THE LABEL ATOMICITY LAW. These are the routing labels the canonical control
      configuration declares (routing.escalation_label and routing.destination_label), resolved
      through the single resolver and never typed here. The venue item MUST be created carrying
      them IN THE SAME forge call that creates it. In generation 1 the labels were applied 10
      minutes 25 seconds after the issue was opened, so for ten minutes the request sat in the
      venue without its declared routing metadata and any label-keyed discovery path could not
      have fired; latency measured from creation was then not latency from routability (observer
      finding 4.6). The emitter's post-condition is checked against the CREATION RESPONSE, not
      against a later read: a label present on a later read does not establish that it was
      present at creation.
  - publication_redaction: The declared, digested redaction contract for evidence published to a
      public venue, carried in the envelope so a third party can check the claim rather than
      trust the prose.
